# 네이티브 라이브러리 통합은 하드 의존이 아니라 인터페이스 주입으로

순수 Dart 라이브러리가 네이티브(FFI) 라이브러리의 기능을 필요로 할 때,
그 의존을 라이브러리에 박는 대신 최소 계약(interface)을 정의하고 소비자가
구현을 주입하게 만든다. g2pkk의 `MorphAnalyzer`(`pos()` → (surface, tag) 목록)가
이 패턴이고, mecab.dart 어댑터는 소비자 쪽 10줄 짜리 접착제다.

## The Rule

- 라이브러리 코어는 **제로 런타임 의존**을 유지하고, 네이티브가 필요한 기능은
  추상 계약(메서드 시그니처 + 데이터 계약)만 갖는다.
- 계약은 포장할 원본의 실제 사용면을 그대로 미러링한다(python-mecab-ko의
  `pos()` 관례·mecab-ko 태그 체계) — 포트 충실성이 곧 검증 가능성이다.
- 주입이 없으면 기존(주입 전) 동작 100% 보장 — 기본값 null, 선택 기능.
- 어댑터의 소유권(생성·해제)도 소비자에게 있다(생성자 주입).

## Why it works

- 순수 Dart 소비자(별도 빌드 없이 `dart test`만 돌어야 하는 CLI·라벨러)가
  네이티브 빌드 부담을 강제받지 않는다.
- 네이티브 바인딩의 빌드 문제(이 머신에서 hosted mecab 0.1.0 Windows 빌드
  파손 → 포크로 override하는 실정)가 라이브러리 의존 그래프를 오염시키지
  않는다 — 문제가 소비자 영역에 국한된다.
- 계약이 원본 관례를 미러링하므로 원본(Python g2pK)과의 출력 정합 검증이
  페이크 어널라이저(매핑 테이블)만으로 단위 테스트된다.

## Trade-offs

- 마커를 내지 않는 품사는 경계 정보가 소실된다 — 계약 밖 정보(부사 MAG)가
  필요해지면 계약 자체를 확장해야 한다([[g2pkk-mecab-less-limits]]의
  어절 경계 삽입 사례). 원본에 없는 확장은 원본과의 출력 격차(라벨↔추론
  이원화)를 만들 수 있어 계약 문서로 명시한다.
- 어댑터를 여러 소비자가 중복 구현할 수 있다 — 접착제가 10줄을 넘으면
  공유 패키지로 승격할 때다.

## Anti-Pattern

- 라이브러리 pubspec에 FFI 패키지를 직접 넣기 — 한 소비자의 빌드 파손이
  전체 생태계를 오염시킨다.
- 계약을 '깔끔하게' 재설계하기(원본 관례 버리고 자체 모델) — 원본과의
  정합 검증이 사라진다.
- 라이브러리 안에서 분석기 인스턴스를 생성/소유하기 — isolate·프로세스
  수명과 충돌한다.
